## UX overhaul（Unity Visual Scripting より簡単にする）

調査は `docs/04-ux-audit.md`。シナリオ A（Title → Game → Result → Title をボタンで進めて Play、5 分）と B（コンテナで Pause、Result から Retry、Play 中に現在地を確認）を
速く・短く・迷わなくするものだけを入れる。優先度順。手数は監査の数え方（A・B とも現状 93 手 + コード）での見積もり。サイズは S / M / L。

| 優先 | 項目 | 直す所（監査） | 見込み | サイズ |
|---|---|---|---|---|
| 1 | **新しいグラフに Entry を自動で置き、空のキャンバスに案内を出す**。案内には「Add first Scene」（Entry に繋いだ Scene ノードを作る）と、ノードの追加方法（Space / 右クリック）。空のコンテナにも同様の案内 | A-2・A-3、B-3（F1, F2, F14） | A で −4 手。初めての人が最初の Error で止まらない | S |
| 2 | **ボタン用のコンポーネント `Graph Event Button`**（Runtime）。UI Button に付けると、クリックでそのグラフを実行中の Runner に Raise（または Advance）する。イベント名はグラフにある名前からドロップダウンで選ぶ。Runner への参照は不要（`GraphRunner.Running` から探す） | A-9・A-10、B-8（F7, F11） | A で −7 手、B で −12 手（ボタン 1 つにつき 6 手）。何より**コードが要らなくなる**（シナリオ A を 5 分で通すための必須項目） | M |
| 3 | **ワンクリック Play**（ツールバーの「Play」）。グラフのシーンを Build Settings に入れ（最初の Scene ノードのシーンを index 0 へ。並びを変える前に確認する）、最初のシーンにこのグラフの Graph Runner が無ければ確認して追加・保存し、最初のシーンを開いて Play に入る。あわせて「このグラフを使う Graph Runner が Build Settings のシーンに無い」を検証の Warning に（シーンの依存関係にグラフが含まれるかで判定。安価） | A-7・A-8・A-11（F9, F10, F12） | A で −8 手。Runner を置くためにウィンドウを出る作業が無くなる | L |
| 4 | **シーンアセットをキャンバスへドロップすると Scene ノードを作る**（複数選択なら並べて作る）。Scene ノードはタイトル未入力ならシーン名をタイトルに出す | A-4（F3, F4） | A で −21 手（3 つのシーンを選んで 1 回ドロップ） | M |
| 5 | **ポートから空き地へエッジを落とすと、繋げる型だけの検索を開き、作って繋ぐ**（待機ノードの出力からなら Event を先頭に） | A-6、B-4・B-7（F5） | A で −6 手、B で −4 手 | M |
| 6 | **イベント名を選べるようにする**: Event ノードのインスペクタで、グラフ内の既存の名前をドロップダウンで選べる（新しい名前は入力）。大文字小文字・前後の空白だけが違う名前を検証で警告。右クリック「Copy Raise Call」で `Raise("…")` をコピー | A-6・A-9、B-4（F7） | 入力の手間と食い違いを無くす（項目 2 のドロップダウンと同じ一覧を使う） | M |

| 8 | **Play 中のデバッグ**: 現在のノードのインスペクタに「Now running」と、そこから出せるイベントのボタン（Raise / Advance）を出す。Blackboard に実行中の値を出す。直近に通ったノードを薄く残す（軌跡） | B-9（F15） | ボタンをシーンに置かなくても流れを確かめられる。B の確認が 2〜3 手に | M |

## 未決事項
- ポートの型システムを持つか（当面は文字列名のみ、型なし）
- Entity / System ノードの粒度と、それが既存ゲームプロジェクトのアーキテクチャとどう対応するか
- Git URL 配布時の `Samples~` の扱い
- コンテナ: ルート階層の始め方（今はルートの `EntryNode`。コンテナの Entry と型を統一するか、専用の Start ノードにするか）
- コンテナ: Exit に対応する出力ポートが繋がっていないときのランタイムの扱い（止める / エラー / 警告）。**当面は**、直前の待機ノードに留まって警告を出す
- コンテナ: 「選択範囲をコンテナにまとめる」コマンド（範囲の境界をまたぐエッジを Entry / Exit に置き換える）
- コンテナ: コンテナの中身を、外の階層でもプレビュー表示するか
- ノードの振る舞い: `OnLateUpdate` や物理・入力のコールバック（`OnTriggerEnter` 相当）まで持たせるか（当面は Enter / Update / FixedUpdate / Exit のみ）
- ノードの振る舞い: コンテナにも付けるか（コンテナの中にいる間ずっと動く、サブステートマシン相当。当面は State・Scene のみ）
- UX: **条件付き遷移**（提案のみ。承認まで実装しない）。Animator の遷移のように、Blackboard の値で遷移する（例: `Lives <= 0` → GameOver）。
  ロジックのグラフにはせず、宣言的な設定にとどめる。素描:
  - Event ノードに「条件」の一覧（パラメータ・比較演算子・値。すべて満たすとき有効）と、モード（Raise されたときだけ／自動）を足す。
    自動モードは名前の無い遷移で、現在のノードにいる間に条件が満たされたら進む（`ParameterChanged` と、ノードに入った直後に判定）
  - 演算子はパラメータの型で絞る（Bool: is true / is false、Int / Float: `==` `!=` `<` `<=` `>` `>=`、String: `==` `!=`）。パラメータは Blackboard から選ぶ（名前を打たない）
  - 検証: 存在しないパラメータ・型の合わない比較を Error、同じノードから同時に満たされうる自動遷移を Warning
  - 未決: 条件を Event ノードに持たせるか、エッジに持たせるか。自動遷移の判定を毎フレーム行うか、値の変化時だけにするか
- UX: イベント名の定数クラスを生成するか（骨組みコード生成の一部。`GraphEvents.StartGame` のように書けて打ち間違いが無くなるが、生成物の置き場所と更新のタイミングを決める必要がある）
- UX: シナリオの所要時間は実機で計測する（`docs/04-ux-audit.md` の現状は机上の通しによる手数と見積もり）
